# acp-sdk: 2.9.1 to 2.12.0

## In short

- Upstream changed one ACP v2 type that we copy: `MessageMcpRequest` (`mcp/message`, unstable) gains optional `sessionId` and `toolCallId`. A `toolCallId` now requires a `sessionId`. No method, other type, capability or `x-state` rule changed.
- The rest is about description rewording. Titles, names and labels are now described as plain text, and text blocks should be joined without a separator. Our kits already do both for the text they show.
- The update is small: replace the pinned schema file, regenerate, and run the existing suites. On the evidence here, no addon, profile or recording has to change.
- Claude's adapter (0.109.1) advertises ACP-transport MCP, so the new fields could matter to us one day. We do not use that path today, and we could not confirm what the daemon does with an incoming `mcp/message`.

## What changed upstream

Only the two schema files and the changelog are in scope. The diff has two files: `schema.json` (lines 1–329) and `schema.unstable.json` (lines 330 on). We pin the unstable one.

**MCP over ACP (unstable, `schema.unstable.json` only):**
- `MessageMcpRequest` gains `sessionId` (`SessionId`, or null): "the session whose work caused this request", which the Agent "SHOULD include" and "MUST NOT" fill with another session's ID.
- It gains `toolCallId` (`ToolCallId`, or null): the tool call in that session, which the Agent "MUST NOT send ... without `sessionId`".
- `x-scope` gains `"session": ["sessionId"]` and `"toolCall": ["toolCallId"]`.
- A new `if`/`then` makes `sessionId` required when `toolCallId` is present.
- The changelog says 2.10.0 and 2.11.0 added the MCP-over-ACP admit check, so a server can require or reject a session. 2.12.0 added a cancellation signal to the MCP bridge's attribution resolver. These are SDK features, not schema changes.

**Description-only rewording (both files):**
- Titles, names, labels, descriptions, permission-prompt titles, form fields, error messages and command names are now marked "plain text".
- Text content blocks: "Clients SHOULD join adjacent text blocks without a separator before rendering." Text payloads "may be plain text or Markdown".
- Resource content: "Its `mimeType`, when provided, describes the format."

**Unchanged:** `methodsAdded`, `methodsRemoved`, `typesAdded`, `typesRemoved` and `stateRulesChanged` are all empty. The only `typesChanged` entry is `MessageMcpRequest`. I checked the non-description lines of the diff, and only the `MessageMcpRequest` lines are structural.

## What it touches here

**`schema/acp-v2.schema.json`.** Our copy is the 2.9.1 unstable file. Three of its description strings match the "before" side of the diff, so the pin is the 2.9.1 text. Replacing it is the single deliberate change that `schema/README.md` asks for. Our `MessageMcpRequest` (lines 2776–2818) lacks the two new fields.

**`schema/state-rules.json` and the generated copies.** These are unaffected. `crates/archipel-schema/src/rules.rs` reads only `x-state`, and `tools/watch/lib.ts` says so explicitly ("the rule generator reads nothing else"). `stateRulesChanged` is empty. So `just gen` should leave `schema/state-rules.json`, `clients/ts/src/generated/state-rules.json` and `clients/swift/.../state-rules.json` unchanged. A diff there would be surprising and worth investigating.

**Rust crate.** `crates/archipel-schema/Cargo.toml` pins `agent-client-protocol-schema` 1.21.2 with the `unstable` and `unstable_protocol_v2` features. The schema file and the crate are meant to move together. I could not check whether a crate release matching 2.12.0 exists or already has the new fields (see below).

**Addons (`crates/archipel-addons`).** Neither addon's fault is touched.
- `acp.restore-settings` works around `configOptions` on `session/resume`. The diff does not change that.
- `pi.check-setting-values` works around `pi-acp` accepting any setting value. The diff does not change setting validation.

Upstream has not repaired either fault, so neither addon can go.

**Profiles (`crates/archipel-agents`).**
- Claude: `testdata/transcripts/claude-v2/simple.ndjson` line 3 shows the adapter's `initialize` result with `"version":"0.109.1"` and `"mcp":{"stdio":{},"http":{},"acp":{}}`. So the Claude adapter supports `acp` MCP servers. The daemon passes the default agent's capabilities through unchanged (`crates/archipel-server/src/daemon.rs` around 957–970), so apps can see that flag. It also stores each session's `mcpServers` and sends them back on resume (`daemon.rs` 1493, 1753, 3425).
- Pi: the Pi recording does not advertise `acp` (no hits in `testdata/transcripts/pi-v2/simple.ndjson`). `crates/archipel-agents/src/pi.rs` forwards `mcpServers` to `pi-acp` unchanged (324–328, 425). `docs/research/37` says `pi-acp` drops them. The changed type is v2-only, so the v1 translation has nothing to change.
- The daemon has no handler for `mcp/message`. A request of that kind from an adapter would arrive on the generic path, and I did not trace what that path does with it.

**Recordings (`testdata/transcripts`).** Nothing I found requires re-recording. A session needs an `acp` MCP server to produce `mcp/message`, and no recording I looked at declares one. A grep for `mcp/message` across both directories would settle that.

**Conformance (`conformance/baseline`).** `session.mcp_server` (`conformance/scenarios.ts` 463–475; baseline `claude.json` line 362 and `pi.json` line 198) passes a stdio server only. It is unaffected.

**Client SDKs and kits.**
- No code under `clients/`, `ui/react/src` or `ui/swift/Sources` names `mcp/message` or the new fields.
- No new item kind, method or capability appears in the diff.
- Our React kit already joins text blocks with no separator (`ui/react/src/items.tsx:40`, `.join("")`), which matches the new wording.
- Only agent text is drawn as Markdown (`ui/react/src/chat.tsx:189`, `items.tsx:58`). Titles and labels are not, which matches "plain text".

## Proposed steps

1. **Replace the pinned schema alone.** Copy `schema.unstable.json` from 2.12.0 over `schema/acp-v2.schema.json`, with no other edits. Run `just gen`. Expect `git status` to show only the schema file and no change to any generated file. Then run `cargo fmt --all --check && cargo clippy --workspace --all-targets -- -D warnings`, `cargo test --workspace` (this includes the test that parses every recorded update with the crate), `pnpm -r check && pnpm -r test` after `cargo build`, and `swift test`. Expected: all pass unchanged.
2. **Bump `agent-client-protocol-schema` only if step 1 needs it.** If the crate at 1.21.2 lacks the new `MessageMcpRequest` fields, move to the matching release in the same change, as `schema/README.md` requires. A test that builds a `mcp/message` request with `sessionId` and `toolCallId` would show whether the crate has them.
3. **Before anyone relies on ACP-transport MCP, probe it.** Start a real Claude session (the cheapest model) with one `{"type":"acp",...}` server in `mcpServers`, and record what reaches the daemon. This settles how the daemon handles `mcp/message` today. It needs a decision on whether we support that path at all. If we do, add a conformance scenario beside `session.mcp_server`.
4. **Check the Swift kit's text joining** (`ui/swift/Sources/ArchipelUI`) against "join adjacent text blocks without a separator". I only checked the React kit.
5. **Do not re-record transcripts** on this evidence. Re-record only if step 1 breaks a recorded-update test.

## What I could not judge

- **Whether a matching `agent-client-protocol-schema` crate exists**, and whether 1.21.2 already has the new `MessageMcpRequest` fields. I could not inspect the cargo registry from here, and I did not check the network. Step 1's `cargo test` settles this.
- **What the daemon does with an incoming `mcp/message`.** I read the relevant code paths but did not trace them to the end. Step 3 is the test.
- **Which beta our pinned file corresponds to.** The 2.10.0 changelog mentions "schema v1.35.0 and v2.0.0-beta.4". I matched text against the 2.9.1 side of the diff, but not against any named beta.
- **Whether the `@agentclientprotocol/sdk` package itself is a dependency of ours.** I found no `package.json` entry for it in `clients/ts`, `ui/react` or `tools/watch`. If it is not, the SDK-side MCP changes in 2.10–2.12 do not reach us at all. I did not confirm this with a full search.
- **Whether the `sessionId`/`toolCallId` scoping matters to the daemon's routing.** Nothing in `crates/` reads `x-scope`, so I believe it does not. I did not confirm that by reading the daemon's routing code end to end.
- **Whether a Markdown-rendering path shows any plain-text field.** I checked the React kit. I did not check the Swift kit or the TypeScript client's own text handling.
